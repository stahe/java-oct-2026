    7. Interfaces fonctionnelles, lambdas et événements

    Dans de nombreux programmes, on a besoin de passer à une méthode non pas une donnée, mais un comportement : le critère d'un tri, la condition d'un filtrage, le traitement à exécuter quand quelque chose se produit. Java répond à ce besoin avec une notion simple, sur laquelle tout ce chapitre repose : l'interface fonctionnelle, c'est-à-dire une interface qui ne déclare qu'une seule méthode abstraite. Un objet qui implémente une telle interface « transporte » une fonction, que l'on peut ranger dans une variable, passer en paramètre, rendre comme résultat d'une méthode, et exécuter quand on le souhaite.

    Avant Java 8 (2014), il fallait écrire une classe, souvent une classe anonyme, pour chaque comportement à transmettre, ce qui était verbeux. Java 8 a introduit les expressions lambda et les références de méthodes, qui permettent d'écrire ce comportement en une ligne. Nous les avons déjà utilisées sans les détailler avec l'API Stream au chapitre 5 : dans [personnes.stream().filter(p -> p.age() >= 18)], on passe une lambda, donc l'instance d'une interface fonctionnelle, à la méthode [filter]. Ce chapitre explique ce qui se cache derrière cette écriture. Il se termine par les événements, que Java gère avec des écouteurs (« listeners ») : des objets, souvent des lambdas, qui s'inscrivent auprès d'un émetteur pour être avertis de ce qui s'y passe. Les interfaces graphiques Java (Swing, JavaFX) comme les frameworks web reposent sur ce mécanisme : un clic sur un bouton, l'arrivée d'une requête HTTP sont signalés à des écouteurs inscrits. Ce cours ne traite pas des interfaces graphiques : tous les exemples sont des programmes console.

    Les programmes du chapitre sont des fichiers source compacts, dans le dossier [07-lambdas]. On les exécute par [java LambdasNN.java]. Rappelons qu'un fichier source compact importe automatiquement tout le module [java.base] : les interfaces des paquetages [java.util.function], [java.util] ou [java.util.concurrent] y sont utilisables sans aucune instruction [import].

    7.1. Les interfaces fonctionnelles prédéfinies

    7.1.1. La notion d'interface fonctionnelle

    Une interface fonctionnelle est une interface qui a exactement une méthode abstraite. Elle peut avoir par ailleurs autant de méthodes [default] et [static] qu'on le souhaite (cf. chapitre 4) : elles ne comptent pas. Cette unique méthode abstraite décrit un modèle (on dit aussi une signature, ou une forme) de fonction : les types de ses paramètres et le type de son résultat. Une variable du type de l'interface peut alors référencer n'importe quel objet qui fournit une fonction de cette forme, et l'exécuter en appelant la méthode.

    L'exemple le plus ancien est l'interface [java.lang.Runnable], qui existe depuis Java 1.0 et qui représente une tâche à exécuter (nous la retrouverons avec les threads au chapitre 8). Elle se réduit à une méthode : [void run();]. Elle décrit une fonction :

    • sans paramètre ;
    • ne rendant aucun résultat ([void]).

    Il existe trois façons de créer un objet de type [Runnable] :

    • écrire une classe qui implémente l'interface, nommée ou anonyme. C'était la seule façon de faire avant Java 8 ;
    • écrire une expression lambda : [Runnable tache = () -> IO.println("tâche");] ;
    • écrire une référence de méthode vers une méthode existante qui a la bonne forme : [Runnable tache = Fonctions::afficher;].

    Dans les deux derniers cas, le compilateur crée lui-même l'objet qui implémente l'interface : la lambda ou la méthode référencée devient le corps de la méthode [run]. On exécute ensuite la fonction en appelant la méthode de l'interface : [tache.run()]. Contrairement à d'autres langages, Java n'a pas de syntaxe d'appel particulière : on appelle toujours la méthode de l'interface par son nom ([run], [apply], [test]…).

    7.1.2. Les interfaces du paquetage java.util.function

    Avant Java 8, chaque bibliothèque définissait ses propres interfaces à une méthode ([Runnable], [Comparator], [ActionListener]…). Java 8 a ajouté le paquetage [java.util.function], qui fournit 43 interfaces fonctionnelles génériques couvrant la quasi-totalité des besoins. Les principales sont les suivantes :

    Les génériques Java ne s'appliquent qu'aux types objets : une [Function<Integer, Integer>] reçoit et rend des [Integer], ce qui impose des conversions automatiques (boxing et unboxing) entre [int] et [Integer]. Pour les éviter, le paquetage propose des versions spécialisées pour les types primitifs [int], [long] et [double] : [IntBinaryOperator] ([int applyAsInt(int left, int right)]), [IntUnaryOperator], [IntPredicate], [IntSupplier], [IntConsumer], [IntFunction<R>] (un [int] en paramètre), [ToIntFunction<T>] (un [int] en résultat), et leurs équivalents [Long…] et [Double…]. Il n'existe pas d'interface prédéfinie à trois paramètres ou plus : il faut alors définir la sienne (paragraphe suivant).

    // les interfaces fonctionnelles prédéfinies de Java

void main() {
    // 1 - Runnable : aucun paramètre, aucun résultat : void run()
    Runnable tache = new Runnable() {
        @Override
        public void run() {
            Fonctions.afficher();
        }
    };
    // forme abrégée : une référence de méthode
    tache = Fonctions::afficher;
    // exécution : on appelle l'unique méthode abstraite de l'interface
    tache.run();

    // 2 - BiFunction<T, U, R> : deux paramètres, un résultat
    BiFunction<Integer, Integer, Integer> operation = Fonctions::ajouter;
    IO.println("operation.apply(2, 3)=" + operation.apply(2, 3));
    // Supplier<T> : aucun paramètre, un résultat
    Supplier<String> saluer = Fonctions::saluer;
    IO.println("saluer.get()=" + saluer.get());
    // version primitive : IntBinaryOperator, int applyAsInt(int, int), sans boxing
    IntBinaryOperator multiplier = Fonctions::multiplier;
    IO.println("multiplier.applyAsInt(2, 3)=" + multiplier.applyAsInt(2, 3));

    // 3 - Consumer<T> : un paramètre, pas de résultat
    Consumer<String> ecrire = IO::println;
    ecrire.accept("Consumer<String> a exécuté IO.println");

    // 4 - Predicate<T> : un paramètre, un résultat boolean
    Predicate<Integer> estPair = Fonctions::estPair;
    IO.println("estPair.test(8)=" + estPair.test(8));
    List<Integer> nombres = new ArrayList<>(List.of(3, 8, 1, 6, 5, 4));
    // removeIf de Collection attend un Predicate
    boolean modifiee = nombres.removeIf(estPair);
    IO.println("nombres pairs retirés : " + modifiee + ", reste : " + nombres);

    // 5 - Comparator<T> : deux paramètres T, un résultat int
    List<String> noms = new ArrayList<>(List.of("Paul", "Mélanie", "Jo", "Sébastien"));
    noms.sort(Fonctions::comparerLongueurs);
    IO.println("triés par longueur : " + noms);

    // 6 - une lambda est un objet : l'instance d'une classe générée qui implémente l'interface
    IO.println("classe : " + operation.getClass().getName());
    IO.println("interfaces : " + Arrays.toString(operation.getClass().getInterfaces()));
}

// les méthodes référencées, regroupées dans une classe
// (la classe implicite d'un fichier source compact ne peut pas être nommée)
class Fonctions {

    static void afficher() {
        IO.println("afficher() exécutée par Runnable.run()");
    }

    static int ajouter(int n1, int n2) {
        return n1 + n2;
    }

    static int multiplier(int n1, int n2) {
        return n1 * n2;
    }

    static String saluer() {
        return "Bonjour";
    }

    static boolean estPair(int n) {
        return n % 2 == 0;
    }

    static int comparerLongueurs(String s1, String s2) {
        return Integer.compare(s1.length(), s2.length());
    }
}

    • lignes 44-45 : une référence de méthode, comme une lambda, est un objet. Une lambda n'est donc pas un nouveau genre d'objet : c'est l'instance d'une classe ordinaire qui implémente une interface fonctionnelle.

    7.2. Définir ses propres interfaces fonctionnelles

    Les interfaces prédéfinies suffisent souvent, mais on peut définir les siennes. Il suffit d'écrire une interface ayant une seule méthode abstraite, par exemple :

    • [interface Operation { int calculer(int n1, int n2); }]

    Cette interface représente une fonction acceptant deux entiers et rendant un entier. Par rapport à [IntBinaryOperator], le type [Operation] a un nom qui dit à quoi il sert, sa méthode a un nom parlant ([calculer] plutôt que [applyAsInt]), et ses paramètres ont des noms ([n1], [n2]) que les outils de développement affichent. On la fait précéder de l'annotation [@FunctionalInterface] : elle n'est pas obligatoire, mais elle demande au compilateur de vérifier que l'interface est bien fonctionnelle, et elle documente l'intention du développeur.

    Une variable [op] de type [Operation] ne référence qu'une seule fonction à la fois. Contrairement à d'autres langages, qui offrent des « délégués multicast », Java n'offre pas de moyen d'enregistrer plusieurs fonctions dans une même variable pour les exécuter toutes d'un seul appel : quand on en a besoin, on range les fonctions dans une liste et on les exécute une à une. C'est exactement ce que nous ferons avec les écouteurs d'événements.

    // définir ses propres interfaces fonctionnelles

void main() {
    // une variable de type Operation reçoit la méthode statique augmenter
    Operation op = Calculs::augmenter;
    // on exécute l'opération
    int n = op.calculer(4, 7);
    IO.println("n=" + n);

    // création d'un objet c1 de type Calculs
    var c1 = new Calculs();
    // on range dans op la méthode ajouter de l'objet c1
    op = c1::ajouter;
    n = op.calculer(2, 3);
    IO.println("n=" + n);
    // puis la méthode soustraire de c1
    op = c1::soustraire;
    n = op.calculer(2, 3);
    IO.println("n=" + n);

    // une variable ne référence qu'une fonction : pour en exécuter plusieurs, on utilise une liste
    List<Operation> operations = new ArrayList<>();
    operations.add(c1::ajouter);
    operations.add(c1::soustraire);
    operations.add((n1, n2) -> n1 * n2);
    for (Operation operation : operations) {
        IO.println("-> " + operation.calculer(10, 4));
    }

    // une méthode default de l'interface construit une nouvelle opération
    Operation sommeAuCarre = ((Operation) c1::ajouter).puis(x -> x * x);
    IO.println("sommeAuCarre.calculer(1, 2)=" + sommeAuCarre.calculer(1, 2));

    // Operation et IntBinaryOperator ont la même forme mais sont deux types différents
    IntBinaryOperator autre = op::calculer;
    IO.println("autre.applyAsInt(5, 1)=" + autre.applyAsInt(5, 1));

    // une interface fonctionnelle générique
    Transformation<String, Integer> longueur = String::length;
    Transformation<Integer, String> etoiles = "*"::repeat;
    IO.println("longueur(\"Bonjour\")=" + longueur.transformer("Bonjour"));
    IO.println("etoiles(5)=" + etoiles.transformer(5));
}

// définition d'une interface fonctionnelle : une seule méthode abstraite
// acceptant deux entiers en paramètres et rendant un entier
@FunctionalInterface
interface Operation {
    int calculer(int n1, int n2);

    // une méthode default ne compte pas : l'interface reste fonctionnelle
    default Operation puis(IntUnaryOperator suite) {
        return (n1, n2) -> suite.applyAsInt(calculer(n1, n2));
    }
}

// une interface fonctionnelle générique : T -> R
@FunctionalInterface
interface Transformation<T, R> {
    R transformer(T valeur);
}

// une classe dont les méthodes ont la forme de l'interface Operation
class Calculs {
    // deux méthodes d'instance
    int ajouter(int n1, int n2) {
        IO.println("ajouter(" + n1 + "," + n2 + ")");
        return n1 + n2;
    }

    int soustraire(int n1, int n2) {
        IO.println("soustraire(" + n1 + "," + n2 + ")");
        return n1 - n2;
    }

    // une méthode statique
    static int augmenter(int n1, int n2) {
        IO.println("augmenter(" + n1 + "," + n2 + ")");
        return n1 + 2 * n2;
    }
}

    IntBinaryOperator ajouter = new IntBinaryOperator() {

        public int applyAsInt(int n1, int n2) {

    Une lambda n'est pas tout à fait une classe anonyme abrégée. Dans une classe anonyme, [this] désigne l'instance de la classe anonyme ; dans une lambda, [this] désigne l'objet de la méthode qui entoure la lambda. De plus, une classe anonyme crée une nouvelle portée : elle peut déclarer une variable qui porte le même nom qu'une variable de la méthode, ce qu'une lambda ne peut pas faire. Enfin, une classe anonyme peut implémenter une interface à plusieurs méthodes, ou hériter d'une classe abstraite, ce qui est impossible avec une lambda. Dans le cours, nous utiliserons les lambdas chaque fois que c'est possible.

void main() throws Exception {
    // 1 - une lambda n'a pas de type par elle-même : c'est le contexte qui le fixe
    // var doubler = x -> x * 2;  // refusé : la lambda a besoin d'un type cible
    var doubler = (IntUnaryOperator) x -> x * 2;
    IO.println("doubler(21)=" + doubler.applyAsInt(21));
    // le même texte de lambda peut implémenter deux interfaces différentes
    Supplier<String> fournisseur = () -> "Bonjour";
    Callable<String> appelable = () -> "Bonjour";
    IO.println(fournisseur.get() + " / " + appelable.call());

    // 2 - paramètres déclarés avec var (Java 11) : permet de les annoter ou de les rendre final
    BinaryOperator<String> concatener = (final var s1, final var s2) -> s1 + s2;
    IO.println(concatener.apply("lam", "bda"));

    // 3 - les quatre sortes de références de méthodes
    // a) méthode statique : Classe::methodeStatique
    Function<String, Integer> convertir = Integer::parseInt;
    IO.println("convertir(\"42\") + 1 = " + (convertir.apply("42") + 1));
    // b) méthode d'instance d'un objet donné : objet::methode
    String nom = "Pierre";
    Supplier<String> enMajuscules = nom::toUpperCase;
    IO.println("enMajuscules.get()=" + enMajuscules.get());
    // c) méthode d'instance d'un objet quelconque : Classe::methodeInstance
    //    l'objet sur lequel la méthode est appelée devient le premier paramètre
    UnaryOperator<String> majuscules = String::toUpperCase;
    Comparator<String> ignorerCasse = String::compareToIgnoreCase;
    IO.println("majuscules(\"paul\")=" + majuscules.apply("paul")
            + ", ignorerCasse(\"abc\", \"ABC\")=" + ignorerCasse.compare("abc", "ABC"));
    // d) constructeur : Classe::new
    Supplier<List<String>> creerListe = ArrayList::new;
    Function<String, StringBuilder> creerTampon = StringBuilder::new;
    IntFunction<int[]> creerTableau = int[]::new;
    List<String> liste = creerListe.get();
    liste.add("élément");
    IO.println(liste + " " + creerTampon.apply("abc").reverse() + " " + creerTableau.apply(3).length);

    // 4 - les exceptions contrôlées : Callable.call peut en lancer, Supplier.get non
    Callable<Integer> lire = () -> {
        throw new IOException("fichier absent");
    };
    try {
        lire.call();
    } catch (IOException ex) {
        IO.println("exception reçue : " + ex.getMessage());
    }

    // 5 - chaque évaluation d'une lambda ou d'une référence de méthode peut créer un nouvel objet
    Supplier<String> r1 = nom::toUpperCase;
    Supplier<String> r2 = nom::toUpperCase;

      • ligne 23 : la référence à une méthode d'instance d'un objet donné, [objet::methode]. [nom::toUpperCase] est équivalente à [() -> nom.toUpperCase()] : l'objet [nom] est fixé une fois pour toutes ;

[String::toUpperCase] est équivalente à [s -> s.toUpperCase()] (un paramètre), et [String::compareToIgnoreCase] à [(s1, s2) -> s1.compareToIgnoreCase(s2)] (deux paramètres), d'où un [Comparator<String>] ;

    • ligne 37 : on utilise les trois fonctions de création ; [reverse] inverse le contenu du [StringBuilder] (ligne 8 des résultats) ;
    • lignes 40-47 : une différence importante entre [Callable] et [Supplier]. La méthode [call] est déclarée [throws Exception] : une lambda de type [Callable] peut donc lancer une exception contrôlée (cf. chapitre 3), ici une [IOException]. La méthode [get] de [Supplier] ne déclare aucune exception : la même lambda de type [Supplier<Integer>] serait refusée ([unreported exception IOException; must be caught or declared to be thrown]). Aucune interface de [java.util.function] n'autorise les exceptions contrôlées : une lambda qui en provoque une doit l'intercepter elle-même, ou utiliser une interface dont la méthode la déclare. C'est pourquoi [main] est déclarée [throws Exception] (ligne 3) : les appels [appelable.call()] (ligne 11) et [lire.call()] (ligne 44) peuvent en théorie lancer une [Exception] quelconque, que le [catch] de la ligne 45, limité à [IOException], n'intercepte pas ;
    • lignes 50-52 : deux évaluations de la même référence de méthode [nom::toUpperCase] produisent deux objets différents, que ni [==] ni [equals] ne considèrent comme égaux (ligne 10 des résultats). Retenons-le : il aura son importance pour désinscrire un écouteur d'événement.

            List.of(String::strip, String::toLowerCase, s -> s.replace(' ', '-'));

        normaliser = normaliser.andThen(etape);
    }

    Predicate<String> court = s -> s.length() <= 4;
    Predicate<String> commenceParP = s -> s.startsWith("P");

    IO.println("non court : " + filtrer(prenoms, court.negate()));
    IO.println("non vides : " + filtrer(List.of("a", "", "b"), Predicate.not(String::isEmpty)));

    List<String> journal = new ArrayList<>();
    Consumer<String> afficher = s -> IO.println("affichage : " + s);
    Consumer<String> memoriser = journal::add;
    Consumer<String> lesDeux = afficher.andThen(memoriser);
    lesDeux.accept("premier");
    lesDeux.accept("second");

static <T> List<T> filtrer(List<T> elements, Predicate<? super T> predicat) {
    List<T> resultat = new ArrayList<>();
    for (T element : elements) {
        if (predicat.test(element)) {
            resultat.add(element);
        }
    }
    return resultat;
}

    int autreSeuil = 10;

    // int total = 0; IntConsumer cumuler = n -> total += n;  // refusé
    // ... mais elle peut modifier l'objet qu'elle référence
    AtomicInteger total = new AtomicInteger();

    cumuler.accept(3);
    cumuler.accept(4);
    IO.println("total=" + total.get());
    // ... ou un champ de l'objet courant (la lambda capture this)
    Runnable compter = () -> nbAppels++;
    compter.run();
    compter.run();
    IO.println("nbAppels=" + nbAppels);

    // 3 - une fermeture : l'objet capturé survit à la méthode qui l'a créé
    IntSupplier compteurA = creerCompteur();
    IntSupplier compteurB = creerCompteur();

    IO.println("B : " + compteurB.getAsInt() + " " + compteurB.getAsInt());

    List<Runnable> actions = new ArrayList<>();
    for (int i = 0; i < 3; i++) {
        // actions.add(() -> IO.print(i + " "));  // refusé : i n'est pas effectivement finale
        int copie = i;
        actions.add(() -> IO.print(copie + " "));
    }
    IO.print("for, capture d'une copie : ");
    actions.forEach(Runnable::run);
    IO.println();

    actions.clear();
    for (int j : new int[] { 0, 1, 2 }) {
        actions.add(() -> IO.print(j + " "));
    }
    IO.print("for-each : ");
    actions.forEach(Runnable::run);

    La règle des variables effectivement finales peut sembler contraignante. Elle a pourtant une justification solide : une lambda peut être exécutée plus tard, ou dans un autre thread (chapitre 8). Si elle pouvait modifier les variables locales d'une méthode peut-être déjà terminée, ou les lire pendant qu'un autre thread les modifie, on aurait des comportements difficiles à prévoir. En imposant des variables qui ne changent pas, Java rend ces situations impossibles ; quand un état modifiable partagé est vraiment nécessaire, on le rend explicite avec un objet ([AtomicInteger], collection…) dont on choisit le comportement vis-à-vis des threads.

    • une interface à plusieurs méthodes reprend l'avantage dès que le comportement à transmettre comporte plusieurs opérations liées entre elles ([calculer] et [nom] ci-dessus), ou qu'il a besoin d'un état et d'une identité propres.

Un [Supplier<List<TrancheImpot>>] aurait techniquement suffi, mais il aurait été beaucoup moins parlant. On réserve donc les interfaces fonctionnelles aux comportements courts et ponctuels (un critère, une transformation, une action), et les interfaces « métier » aux rôles de l'application, quel que soit leur nombre de méthodes.

    7.5. Gestion d'événements

    7.5.1. Le modèle des écouteurs

    Les interfaces fonctionnelles servent à mettre en place des événements. Java n'a pas de mot clé dédié aux événements : il utilise un ensemble de conventions, appelé le modèle des écouteurs (« listener model »), établi dès Java 1.1 pour les composants graphiques et les JavaBeans. Une classe [C1] qui veut signaler un événement [Xxx] procède ainsi :

    • une classe [XxxEvent], dérivée de [java.util.EventObject], encapsule les informations sur l'événement. [EventObject] mémorise l'objet à l'origine de l'événement, qu'on appelle la source et qu'on obtient par [getSource()] ;
    • une interface [XxxListener], qui étend l'interface vide [java.util.EventListener] (une simple marque), définit la ou les méthodes qui seront appelées quand l'événement se produit. Avec une seule méthode, c'est une interface fonctionnelle : un écouteur pourra être une lambda ;
    • la classe [C1] gère une liste d'écouteurs et offre deux méthodes publiques pour s'y inscrire et s'en désinscrire : [addXxxListener(XxxListener l)] et [removeXxxListener(XxxListener l)] ;
    • lorsqu'une instance [c1] de [C1] veut signaler l'événement, elle crée un objet [XxxEvent] et appelle la méthode de chacun des écouteurs inscrits en lui passant cet objet. Par convention, cette notification est confiée à une méthode protégée [fireXxx(XxxEvent e)] (« fire » : déclencher), qu'une classe dérivée peut redéfinir pour modifier la façon dont l'événement est publié ;
    • si un objet [c2] veut être averti de l'événement [Xxx] de l'objet [c1], il s'inscrit par [c1.addXxxListener(...)]. Il pourra se désinscrire par [c1.removeXxxListener(...)] lorsqu'il ne voudra plus être averti. Comme [c1] gère une liste, différents objets peuvent s'inscrire pour être prévenus du même événement.

    Dans ce scénario, on a :

    • une classe qui signale (on dit aussi publie, ou émet) un événement ;
    • des objets qui sont avertis de cet événement. On dit qu'ils s'abonnent, ou s'inscrivent, à l'événement : ce sont les écouteurs (« listeners »), ou gestionnaires d'événement ;
    • une interface d'écoute qui définit la forme des méthodes qui seront averties de l'événement.

    C'est le patron de conception Observateur (« Observer ») : l'émetteur ne connaît pas ses abonnés, il se contente de les avertir. Ce modèle offre la même protection qu'un mot clé dédié : la liste des écouteurs est un champ privé de l'émetteur. De l'extérieur, on ne peut que s'inscrire ou se désinscrire ; on ne peut ni vider la liste, ni remplacer les écouteurs des autres, ni déclencher l'événement à la place de l'émetteur.

class Souscripteur {

    private final String nom;

    // nombre d'alertes reçues
    private int nbAlertes;

    private final TemperatureTropHauteListener ecouteur = this::evtTemperatureTropHaute;

    Souscripteur(String nom, int nbAlertesMax) {
        this.nom = nom;
        this.nbAlertesMax = nbAlertesMax;
    }

    // inscription auprès d'un émetteur
    void abonner(Emetteur emetteur) {
        emetteur.addTemperatureTropHauteListener(ecouteur);
    }

    void desabonner(Emetteur emetteur) {
        emetteur.removeTemperatureTropHauteListener(ecouteur);
    }

    // gestionnaire de l'événement TemperatureTropHaute
    private void evtTemperatureTropHaute(TemperatureTropHauteEvent e) {
        Emetteur emetteur = e.getSource();

                .formatted(nom, emetteur.getNom(), e.getTemperature()));

        nbAlertes++;

            desabonner(emetteur);

    Predicate<Integer> estPair = n -> n % 2 == 0;

        return n > 7;

    IO.println("le flux est défini, rien n'a encore été exécuté");
    grands.forEach(n -> IO.print("-> " + n + " "));
    IO.println();

    // 4 - nos propres opérations intermédiaires avec des collecteurs intermédiaires (Gatherer, Java 24)
    List<String> villes = List.of("Angers", "Paris", "Lyon", "Nantes", "Aix");

            .gather(Outils.filtrer(v -> v.length() <= 5))
            .gather(Outils.transformer(String::toUpperCase))
            .toList();

class Outils {
    // filtre une liste avec un prédicat : le travail que fait filter
    static <T> List<T> filtrer(List<T> source, Predicate<? super T> predicat) {
        List<T> resultat = new ArrayList<>();
        for (T element : source) {
            if (predicat.test(element)) {
                resultat.add(element);
            }
        }
        return resultat;
    }

    static boolean estImpair(int n) {
        return n % 2 != 0;
    }

    // une opération intermédiaire de flux qui ne laisse passer que les éléments vérifiant le prédicat
    static <T> Gatherer<T, ?, T> filtrer(Predicate<? super T> predicat) {
        return Gatherer.of((_, element, aval) -> !predicat.test(element) || aval.push(element));
    }

    // une opération intermédiaire qui transforme chaque élément : l'équivalent de map
    static <T, R> Gatherer<T, ?, R> transformer(Function<? super T, ? extends R> transformation) {
        return Gatherer.of((_, element, aval) -> aval.push(transformation.apply(element)));
    }
}

C'est l'exécution différée (ou paresseuse) des flux. Notre méthode [filtrer], elle, construit toute la liste résultat avant de la rendre ;
    • lignes 51-58 : pour écrire nos propres opérations intermédiaires, paresseuses comme celles de l'API, nous utilisons les collecteurs intermédiaires ([Gatherer], Java 24), le pendant, pour les opérations intermédiaires, des collecteurs ([Collector]) utilisés par [collect]. [Gatherer.of] reçoit une lambda à trois paramètres, appelée pour chaque élément du flux : un état (inutile ici, d'où le paramètre anonyme [_]), l'élément, et l'étage suivant du flux ([aval]), auquel on transmet un élément par [aval.push(...)]. La lambda rend [false] pour arrêter le flux ; les nôtres ne le décident jamais elles-mêmes : elles rendent le résultat de [push], qui ne vaut [false] que si l'aval ne veut plus d'éléments (ou [true] quand le filtre écarte un élément). Le filtre (ligne 52) ne transmet que les éléments qui vérifient le prédicat, la transformation (ligne 57) transmet le résultat de la fonction appliquée à chaque élément ;
    • ligne 56 : [transformer] est doublement générique : [T] est le type des éléments reçus, [R] celui des éléments produits. Le paramètre [Function<? super T, ? extends R>] suit la règle déjà rencontrée : la fonction consomme des [T] et produit des [R] ;
    • lignes 27-30 : la méthode [gather] des flux insère nos opérations dans la chaîne, qui s'écrit comme avec les opérations de l'API : on garde les villes de 5 lettres au plus, puis on les met en majuscules.

    Toute l'API Stream est construite sur ce modèle : des opérations qui reçoivent des interfaces fonctionnelles et produisent de nouveaux flux, dont les éléments ne sont calculés qu'à la demande de l'opération terminale.

    7.7. Les arbres d'expression

    Certains langages, comme C#, permettent de convertir une lambda non pas en code exécutable, mais en une structure de données qui la décrit (un « arbre d'expression ») : un programme peut alors analyser la lambda [t -> t.getLimite() > 20000] et la traduire, par exemple, en une clause SQL [WHERE limite > 20000] exécutée par le serveur de bases de données.

    Java n'a pas d'équivalent. Une lambda Java est toujours compilée en code exécutable : on peut l'appeler, mais on ne peut pas examiner ce qu'elle fait. Les bibliothèques d'accès aux bases de données utilisent donc d'autres moyens pour exprimer une requête. Hibernate, que nous étudierons au chapitre 11, propose deux solutions : un langage de requêtes proche de SQL mais exprimé en termes de classes et de propriétés, HQL (["from Tranche t where t.limite > 20000"]), et l'API Criteria de Jakarta Persistence, qui construit la requête par des appels de méthodes ([cb.gt(t.get("limite"), 20000)]). Dans les deux cas, la requête est une donnée (une chaîne ou un arbre d'objets) que Hibernate traduit en SQL, alors qu'une lambda passée à [filter] s'exécute dans le programme Java.

    7.8. Conclusion

    Nous retiendrons de ce chapitre :

    • une interface fonctionnelle est une interface qui n'a qu'une méthode abstraite. Les interfaces prédéfinies du paquetage [java.util.function] ([Function], [Supplier], [Consumer], [Predicate], leurs variantes à deux paramètres et leurs versions primitives), avec [Runnable], [Callable] et [Comparator], dispensent le plus souvent de définir les siennes ; quand on en définit une, on l'annote [@FunctionalInterface] ;
    • une interface fonctionnelle peut être implémentée par une classe (nommée ou anonyme), par une expression lambda, ou par une référence de méthode ([Classe::statique], [objet::methode], [Classe::methode], [Classe::new]). Une lambda n'a pas de type par elle-même : c'est le type cible qui le fixe ;
    • les lambdas capturent les variables locales qui les entourent, à condition qu'elles soient effectivement finales ; un état modifiable passe par un objet ou un champ ;
    • les méthodes [andThen], [compose], [and], [negate], [comparing], [thenComparing]… construisent de nouvelles fonctions à partir de fonctions existantes ;
    • en Java, une lambda est l'instance d'une interface : on choisit une interface fonctionnelle pour un comportement court et ponctuel, une interface à plusieurs méthodes (ou une interface « métier ») pour un rôle de l'application ;
    • un événement se met en place avec le modèle des écouteurs : une classe [XxxEvent] dérivée d'[EventObject], une interface [XxxListener], des méthodes [addXxxListener] / [removeXxxListener] et une liste d'écouteurs ([CopyOnWriteArrayList]) parcourue par une méthode [fireXxx]. Pour désinscrire un écouteur, il faut conserver l'objet inscrit. [PropertyChangeSupport] fournit ce mécanisme tout prêt pour les changements de propriétés ;
    • l'API Stream est construite sur des opérations qui reçoivent des interfaces fonctionnelles ; Java n'a pas d'arbres d'expression, et Hibernate exprime ses requêtes en HQL ou avec l'API Criteria.

    Les lambdas reviendront dans tous les chapitres suivants : un thread exécute un [Runnable] et un [ExecutorService] un [Callable] (chapitre 8), un [CompletableFuture] enchaîne des fonctions (chapitre 9), et les services web de Spring Boot traitent les requêtes HTTP dans des méthodes que le framework appelle comme des écouteurs (chapitre 13).
